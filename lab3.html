Lab 3 — Device AI Security
Scenario

Capture Cloud LLM traffic is the easy case — it leaves the device, and Zscaler inspects it inline (SSL inspection, DLP, shadow-AI discovery) as demostration with the previous lab. A local LLM running on a laptop is a different problem: inference happens on localhost, the prompt never crosses the network, and nothing inline can see it. Today you'll install Ollama locally, register your AI Guard application and policy, insert a LiteLLM proxy between clients and Ollama, and prove that prompt injection, toxicity, and PII detectors still fire — even though the model itself never touches the wire.

Lab 3 — Proxy Architecture
Inspection Model
Compare Path A (cloud AI) and Path B (local AI) in the diagram above. Why is a local LLM "invisible" to traditional network security, and what does inserting LiteLLM actually change about that?
See Model Answer

Network security products (firewalls, SSL inspection, DLP) only see traffic that crosses the network boundary. Ollama serves the model on localhost:11434 — the prompt and response never leave the device, so there is nothing for an inline network appliance to inspect. The traffic isn't hidden or encrypted past detection; it simply never travels the network at all.

LiteLLM doesn't change the network path — it changes who terminates the connection. The client now talks to LiteLLM on :4000, a local proxy that explicitly calls out to AI Guard's cloud API before and after forwarding to Ollama. This is application-layer instrumentation, not network-layer interception — which is exactly why it works for local inference where nothing inline ever could.

The lab's config.yaml defines two guardrails — one during_call (before Ollama) and one post_call (after Ollama). What's the difference, and why do you need both instead of just one?
See Model Answer

during_call scans the prompt before it ever reaches Ollama — this is what stops prompt injection, jailbreak attempts, or PII from being sent to the model at all. post_call scans the model's response before it reaches the client — this catches secrets, malicious URLs, or leaked data that a completely clean prompt could still elicit.

Running only the during_call guardrail leaves the outbound channel completely unguarded: a benign question like "give me an example of a phishing URL" passes prompt inspection easily, but the model's answer could still contain a live malicious link. Bidirectional inspection closes both the inbound and outbound gap.

Part 1 — Install Locally on the MacBook

Ollama will be used for local inference

Task 3.1 Install Ollama and verify the local API
  1. Install Ollama via Homebrew:
    # Install Homebrew first if needed: https://brew.sh brew install ollama # Start the background service brew services start ollama # or just run: ollama serve # Verify ollama --version

    Or use the official installer: download the macOS app from ollama.com/download, drag to Applications, launch it. It runs a menu-bar service and exposes the same CLI.

  2. Pull and run your first model (downloads on first run):
    ollama pull qwen2.5-coder:14b # download without running ollama list # what's on disk ollama run gemma3:4b # interactive chat ollama rm llama3.1:8b # free disk space ollama ps # what's loaded in memory right now ollama run llama3.1:8b
  3. Verify the OpenAI-compatible REST endpoint. Ollama serves it at http://localhost:11434 — this single fact is what lets you point almost any tool, including a security proxy, at your local model:
    curl http://localhost:11434/v1/chat/completions \ -H "Content-Type: application/json" \ -d '{"model":"llama3.1:8b","messages":[{"role":"user","content":"Say hello"}]}'

    You should see the model reply to what you said ("Say hello").

Part 2 — Zscaler AI Guard: Credentials & Policy

Before traffic can be inspected, AI Guard needs an application, an API key, and an activated policy with detectors on both the prompt and response side.

Task 3.2 Get AI Guard credentials and configure the policy
  1. Log in to the AI Guard console: https://admin.{cloud}.zseclipse.net.
  2. Go to Private AI Apps → Applications; create your application (e.g. AdonisMACAPP).
  3. Go to Private AI Apps → App API Keys; create/copy an API key and associate it with the application. Note your cloud region.
  4. Go to Policies → Configurations; create a policy, enable the detectors you want on prompt (toxicity, injection, PII, secrets, gibberish) and response (PII, secrets, malicious URLs, data leakage), and set each to BLOCK or DETECT. Activate it and note the Policy ID.
  5. Under Policies → Controls, bind the policy to the application + API key so scans auto-resolve the policy without hardcoding an ID.

Part 3 — Insert LiteLLM as the Guardrail Proxy

Raw ollama run has no interception point. LiteLLM is an OpenAI-compatible proxy with a native AI Guard guardrail — inserted between clients and Ollama, the traffic path becomes: Client → LiteLLM :4000 → scan prompt via AI Guard → Ollama :11434 → scan response via AI Guard → Client.

Task 3.3 Install LiteLLM and configure bidirectional guardrails
  1. Prerequisites: Ollama running with a model already pulled (Part 1), plus your AI Guard API key + Policy ID from Part 2.
  2. Install the proxy-enabled version:
    pip install 'litellm[proxy]' mkdir -p ~/aiguard-lab && cd ~/aiguard-lab
  3. Map your credentials as environment variables — keeps sensitive keys out of your config file:
    export ZSCALER_AI_GUARD_API_KEY="your-key" export ZSCALER_AI_GUARD_POLICY_ID="your-policy-id" # Point to the correct regional endpoint if not using us1 export ZSCALER_AI_GUARD_URL="https://api.us1.zseclipse.net/v1/detection/execute-policy"
  4. Define the proxy logic in config.yaml — store it inside the aiguard-lab folder. This file bridges Ollama with bidirectional guardrails, one scanning during_call (prompt) and one post_call (response):
    model_list: - model_name: llama3.1-guarded litellm_params: model: ollama_chat/llama3.1:8b api_base: http://localhost:11434 guardrails: - guardrail_name: "zscaler-ai-guard-during-guard" litellm_params: guardrail: zscaler_ai_guard mode: "during_call" api_key: os.environ/ZSCALER_AI_GUARD_API_KEY policy_id: os.environ/ZSCALER_AI_GUARD_POLICY_ID default_on: true - guardrail_name: "zscaler-ai-guard-post-guard" litellm_params: guardrail: zscaler_ai_guard mode: "post_call" api_key: os.environ/ZSCALER_AI_GUARD_API_KEY policy_id: os.environ/ZSCALER_AI_GUARD_POLICY_ID default_on: true
  5. Start the proxy and point it at your config:
    cd ~/aiguard-lab litellm --config config.yaml --detailed_debug

    The listener sits on port 4000 by default. --detailed_debug is critical to watch the verdicts happen in real-time.

Watch out

The model field under litellm_params (ollama_chat/llama3.1:8b) must exactly match a model you've already pulled with ollama pull in Part 1 — otherwise LiteLLM will forward requests to a model Ollama doesn't have.

Part 6 (Optional) — Troubleshooting

Task 3.6 Test connectivity directly against AI Guard

Bypass LiteLLM entirely and push a prompt straight at the AI Guard detection API to confirm your credentials and Policy ID are valid before debugging the proxy layer.

curl -sS -i -X POST "$ZSCALER_AI_GUARD_URL" \ -H "Content-Type: application/json" \ -H "Authorization: Bearer $ZSCALER_AI_GUARD_API_KEY" \ -d "{\"direction\": \"IN\", \"content\": \"hello world\", \"policyId\": $ZSCALER_AI_GUARD_POLICY_ID}"

Note

The JSON response includes a detectorResponses object per detector (e.g. toxicity, prompt_injection, pii_deepscan), each with its own statusCode, triggered flag, action, and severity — this is the same structure LiteLLM parses to decide ALLOW vs BLOCK.
