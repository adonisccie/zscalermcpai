Inspection Model
AI Guard will inspect both the prompt (going to the model) and the response (coming back). Why does bidirectional inspection matter, and what kind of threat does response inspection specifically address?
See Model Answer

Prompt-only inspection stops users from sending malicious or sensitive content to the model — but a clean prompt can still elicit a harmful response. The model might return a malicious URL, reproduce PII it was trained on, or generate content that violates policy even when the input was benign.

Response inspection closes the outbound gap: it catches malicious URLs in model output, detects data leakage (PII, secrets) in responses, and blocks policy-violating content before it reaches the end user. Without it, AI Guard only defends the input channel — the outbound channel is unguarded.

Every blocked transaction returns a transaction ID and the list of triggered detectors. Why is this important for governance, and how does it relate to frameworks like the NIST AI Risk Management Framework or the EU AI Act?
See Model Answer

A transaction ID ties the block event to a complete audit record: user, application, prompt content, response content, policy applied, detectors triggered, and action taken. This creates an immutable chain of evidence that answers "who sent what, when, under which policy, and what happened."

The NIST AI RMF requires govern, map, measure, and manage controls — AI Guard's transaction log satisfies the measure (detection) and manage (enforcement + logging) pillars. The EU AI Act requires conformity documentation and risk monitoring for high-risk AI systems; AI Guard's per-transaction logs provide the audit trail regulators expect to see.

Part A — Configure the Detection Policy

Detectors and policy. Configruation already done in the SDC.

Task 2.2 Create and activate a detection policy

A policy binds a set of detectors to a specific LLM provider route. When AI Guard sees traffic destined for that provider, it evaluates the policy and applies BLOCK or DETECT actions per detector.

  1. Navigate to AI Guard → Policies.
  2. Click Create Policy (or open the existing lab policy if pre-provisioned).
  3. Enable the following detectors and set their action:
    • Toxicity → BLOCK
    • Prompt Injection → BLOCK
    • Jailbreak → BLOCK
    • PII → BLOCK
    • Secrets / Credentials → BLOCK
    • Malicious URLs → BLOCK (response-side)
    • Competitor / Sensitive Topics → DETECT (logged, not blocked)
  4. Click Activate Policy.
  5. Associate the policy with the provider you registered in Task 2.1.
Verify

The policy status shows Active and is linked to your provider. You should see a green active indicator next to the policy name in the list.

Part B — Console Test Tool (no code needed)

Task 2.3 Open the proxy-mode test tool

AI Guard ships a built-in test tool that lets you send prompts through the proxy pipeline directly from the console — no SDK, no terminal, no test client. This is the recommended demo path for this lab.

  1. Navigate to AI Guard → /b>.
  2. Select your registered provider from the dropdown.
  3. Confirm the active policy is shown in the policy field.
  4. Leave the test tool open — you'll submit prompts here in Task 2.4.
Note

Each test submission shows the verdict (ALLOW or BLOCK) inline, plus the transaction ID and triggering detectors. Keep the console open in a second tab or window so you can cross-reference transaction IDs in the audit log.
